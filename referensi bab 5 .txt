5.1.1.1Kode Program Routing
Routing merupakan bagian yang berfungsi untuk menentukan alur permintaan (request) dari client menuju proses yang akan dijalankan oleh sistem. Melalui routing, setiap endpoint API didefinisikan berdasarkan URL dan metode HTTP yang digunakan, sehingga sistem mengetahui tindakan apa yang harus dilakukan ketika suatu permintaan dikirimkan.
Pada implementasi sistem ini, beberapa metode HTTP digunakan dalam proses routing, di antaranya:
1.GET – digunakan untuk mengambil atau menampilkan data dari server.
2.POST – digunakan untuk mengirimkan data baru dari client ke server.
3.PUT/PATCH – digunakan untuk memperbarui data yang telah tersimpan.
4.DELETE – digunakan untuk menghapus data.

a.Fungsi login(): Fungsi login adalah bagian dari controller autentikasi yang bertugas menangani proses login pengguna ke dalam sistem. Proses autentikasi mencakup validasi kredensial, manajemen device ID, dan pembuatan token JWT untuk sesi pengguna. Pada tahap awal, fungsi membaca data username dan password dari request body, serta device_id dari header request. Data ini kemudian digunakan untuk proses autentikasi dan validasi perangkat. Langkah berikutnya adalah pencarian data user dalam database menggunakan User.findOne() dengan kondisi pencarian berdasarkan username. Jika user tidak ditemukan dalam database, sistem langsung mengembalikan respons kesalahan dengan status 401 Unauthorized dan pesan "Username atau password salah". Proses autentikasi kemudian dilanjutkan dengan verifikasi password menggunakan fungsi bcrypt.compare() untuk membandingkan password yang dikirim pengguna dengan hash password yang tersimpan dalam database. Proses ini menggunakan teknik hashing bcryptjs untuk keamanan, sehingga password tidak pernah disimpan dalam bentuk plain text. Apabila password tidak cocok, sistem kembali mengembalikan respons kesalahan dengan status 401.Setelah verifikasi kredensial berhasil, sistem melakukan validasi dan manajemen device ID. Proses ini dimulai dengan sistem mengecek apakah device ID yang dikirim sudah digunakan oleh akun lain menggunakan User.findOne() dengan kondisi device_id dan id yang berbeda dari user saat ini. Jika device ID sudah digunakan, sistem mengembalikan respons kesalahan dengan pesan "Device ID ini sudah digunakan oleh akun lain". Selanjutnya, jika user belum memiliki device ID yang terdaftar dan header request menyertakan device ID, sistem akan melakukan update device ID untuk user tersebut. Namun, jika user sudah memiliki device ID dan device ID yang dikirim berbeda dengan yang tersimpan, sistem mengembalikan respons kesalahan dengan pesan "Akun ini digunakan di perangkat lain". Mekanisme ini memastikan bahwa setiap akun user biasa hanya dapat digunakan di satu perangkat dalam satu akun, sehingga meningkatkan keamanan sistem.Setelah semua validasi berhasil, sistem membuat token JWT untuk autentikasi sesi. Token payload dibuat dengan menyertakan informasi userId, username, dan level user. Fungsi generateTokens() kemudian dipanggil untuk menghasilkan accessToken dan refreshToken. Access token digunakan untuk autentikasi setiap request ke API, sedangkan refresh token digunakan untuk memperpanjang sesi ketika access token sudah expired. Refresh token yang dihasilkan kemudian disimpan ke dalam database pada kolom refresh_token milik user untuk keperluan validasi dan manajemen sesi.Langkah berikutnya adalah menyusun data respons yang akan dikirim ke client. Data dasar respons mencakup pesan sukses, access token, refresh token, serta informasi user seperti id, username, email, level, status, dan device ID. Apabila terjadi kesalahan pada setiap tahap proses, sistem akan menangkap error melalui blok catch dan mengembalikan respons dengan status 500 Internal Server Error beserta pesan error yang detail. Secara keseluruhan, fungsi login ini menyediakan mekanisme autentikasi yang aman dengan validasi multi-layer, manajemen device ID, dan integrasi dengan database master untuk mendapatkan informasi organisasi yang lengkap. b.Middleware authMiddleware(): Middleware authMiddleware merupakan komponen pengaman yang digunakan untuk memverifikasi akses pengguna setiap kali melakukan permintaan (request) ke API. Middleware ini bertugas memeriksa autentikasi melalui dua metode, yaitu Bearer Access token dan Device ID, sehingga hanya pengguna yang valid yang diizinkan mengakses endpoint tertentu. Proses autentikasi dimulai dengan membaca nilai Authorization dari header request. Jika header tersebut berisi token dengan format "Bearer <token>", sistem akan memisahkan string token dan melakukan proses verifikasi melalui fungsi verifyAccessToken(). Fungsi ini melakukan decoding dan validasi JWT untuk memastikan token masih berlaku dan belum dimodifikasi. Setelah token berhasil diverifikasi, middleware mengambil informasi userId dari payload token, kemudian melakukan pencarian pengguna di database menggunakan User.findByPk(). Middleware mengecek keberadaan header x-device-id. Jika header tidak dikirimkan, proses dihentikan dan respons kesalahan "Authentication diperlukan" dikembalikan. Jika Device ID tersedia, sistem mencari pengguna dengan device ID tersebut menggunakan User.findOne(). Jika ditemukan, informasi user langsung ditempelkan ke req.user, dan request melanjutkan ke proses berikutnya. Middleware juga memiliki opsi konfigurasi allowDeviceAuth. Jika opsi ini disetel false, middleware mewajibkan penggunaan token dan menolak autentikasi berbasis device ID dengan pesan "Access token diperlukan". Seluruh proses autentikasi ini dibungkus dalam blok try-catch untuk menangani potensi kesalahan seperti token kadaluarsa, JWT tidak valid, atau error server internal. Jika terjadi kesalahan yang tidak terduga, middleware mengembalikan respons status 500 dengan pesan "Kesalahan server internal". Secara keseluruhan, authMiddleware menyediakan mekanisme autentikasi berlapis sehingga API tetap aman baik melalui verifikasi akses token maupun identifikasi perangkat. Fungsi createKehadiranBiasa() merupakan controller yang bertugas menangani proses pencatatan kehadiran pegawai pada sistem presensi. 5.1.1.4Kode Program HMAC
Untuk mengamankan transmisi data presensi dari aplikasi mobile ke server, sistem menggunakan HMAC (Hash-based Message Authentication Code). HMAC memastikan integritas dan autentikasi data dengan menghasilkan signature dari payload request menggunakan kunci rahasia bersama. Pendekatan ini mencegah modifikasi data selama transmisi dan memastikan request berasal dari client yang memiliki kunci rahasia yang benar. Pada sub bab ini akan menjelaskan beberapa komponen HMAC yang digunakan pada implementasi sistem yaitu:
1.Fungsi generateHMAC ():
Fungsi generateHMAC () adalah bagian dari utility HMAC yang bertugas menghasilkan signature HMAC dari data yang diberikan. Fungsi ini menggunakan algoritma SHA-256 untuk menghasilkan hash yang aman. Proses dimulai dengan menerima parameter data yang dapat berupa string atau object JavaScript. Jika data berupa object, sistem akan melakukan sorting terhadap kunci-kunci object menggunakan Object.keys(data).sort() untuk memastikan konsistensi format data antara client dan server. Hal ini penting karena urutan properti dalam object JavaScript tidak selalu terjamin, sehingga dengan melakukan sorting terlebih dahulu, sistem memastikan bahwa object yang sama akan menghasilkan string JSON yang identik.Setelah melakukan sorting, data dikonversi menjadi string JSON menggunakan JSON.stringify() dengan parameter kedua berupa array kunci yang sudah diurutkan. String JSON ini kemudian digunakan sebagai input untuk proses hashing. Sistem menggunakan modul crypto dari Node.js untuk membuat instance HMAC dengan algoritma SHA-256 dan secret key yang diambil dari environment variable HMAC_SECRET atau JWT_SECRET. Secret key ini harus sama antara client dan server agar signature yang dihasilkan dapat diverifikasi dengan benar. Proses hashing dilakukan dengan memanggil crypto.createHmac() yang menerima algoritma dan secret key sebagai parameter. Data string kemudian di-update ke dalam instance HMAC tersebut menggunakan method hmac.update(). Signature akhir dihasilkan dengan memanggil hmac.digest('hex') yang mengembalikan signature dalam format hexadecimal string. Apabila terjadi kesalahan pada setiap tahap proses, fungsi akan menangkap error melalui blok try-catch dan mengembalikan error dengan pesan "Gagal menghasilkan HMAC signature". Implementasi fungsi generateHMAC dapat dilihat pada Gambar 5.9 berikut.

2.Fungsi verifyHMAC ():
Fungsi verifyHMAC () adalah bagian dari utility HMAC yang bertugas memverifikasi keabsahan signature HMAC yang diterima dari client. Fungsi ini menerima dua parameter yaitu data yang akan diverifikasi dan signature yang diterima dari request. Sistem memeriksa apakah signature tersedia. Jika signature tidak valid atau kosong, fungsi langsung mengembalikan nilai false yang menandakan signature tidak valid. Setelah validasi awal berhasil, sistem melakukan proses verifikasi dengan membandingkan signature yang diterima dengan signature yang dihasilkan dari data yang sama. Proses ini dimulai dengan memanggil fungsi generateHMAC() menggunakan data yang sama untuk menghasilkan signature yang diharapkan. Signature yang dihasilkan ini kemudian dibandingkan dengan signature yang diterima dari client.Sebelum melakukan perbandingan, sistem memeriksa panjang kedua signature untuk memastikan keduanya memiliki panjang yang sama. Jika panjang signature tidak sama, fungsi langsung mengembalikan nilai false tanpa perlu melakukan perbandingan lebih lanjut.Proses perbandingan signature dilakukan menggunakan crypto.timingSafeEqual() yang merupakan metode perbandingan yang aman terhadap timing attack. Timing attack adalah teknik serangan yang memanfaatkan perbedaan waktu eksekusi untuk mendapatkan informasi tentang data yang dibandingkan. Dengan menggunakan timingSafeEqual(), sistem memastikan bahwa waktu eksekusi perbandingan selalu konstan terlepas dari perbedaan karakter pada signature yang dibandingkan. Fungsi ini menerima dua buffer yang dihasilkan dari konversi signature hexadecimal string menjadi Buffer menggunakan Buffer.from(). Hasil perbandingan ini kemudian dikembalikan sebagai nilai boolean yang menandakan apakah signature valid atau tidak. Apabila terjadi kesalahan pada proses verifikasi, fungsi akan menangkap error melalui blok try-catch dan mengembalikan nilai false. Implementasi fungsi verifyHMAC dapat dilihat pada Gambar 5.10 berikut.

3.Middleware validateHMAC ():
Middleware validateHMAC () merupakan komponen pengaman yang digunakan untuk memvalidasi HMAC signature pada setiap request yang masuk ke endpoint yang dilindungi. Middleware ini bertugas memeriksa autentikasi melalui tiga komponen utama yaitu HMAC signature, timestamp, dan nonce. Kombinasi ketiga komponen ini memastikan bahwa request yang diterima adalah request yang valid, belum pernah digunakan sebelumnya, dan masih dalam batas waktu yang ditentukan, sehingga mencegah berbagai jenis serangan seperti replay attack, man-in-the-middle attack, dan request tampering.Proses validasi dimulai dengan membaca nilai HMAC signature, timestamp, dan nonce dari header request atau body request. Sistem membaca HMAC signature dari header x-hmac-signature atau hmac-signature, timestamp dari header x-timestamp atau body timestamp, dan nonce dari header x-nonce atau body nonce. Fleksibilitas dalam membaca data ini memungkinkan client untuk mengirimkan data melalui header atau body sesuai dengan kebutuhan implementasi.Setelah membaca data dari request, sistem melakukan validasi keberadaan setiap komponen. Jika HMAC signature tidak tersedia, sistem langsung mengembalikan respons kesalahan dengan status 401 Unauthorized dan pesan "HMAC signature diperlukan" beserta kode error HMAC_SIGNATURE_REQUIRED. Jika timestamp tidak tersedia, sistem mengembalikan respons kesalahan dengan pesan "Timestamp diperlukan untuk keamanan" dan kode error TIMESTAMP_REQUIRED. Demikian pula jika nonce tidak tersedia, sistem mengembalikan respons kesalahan dengan pesan "Nonce diperlukan untuk mencegah replay attack" dan kode error NONCE_REQUIRED.Setelah memastikan semua komponen tersedia, sistem melakukan validasi format data. Timestamp divalidasi dengan melakukan konversi ke integer menggunakan parseInt(). Jika hasil konversi menghasilkan NaN (Not a Number), sistem mengembalikan respons kesalahan dengan status 400 Bad Request dan pesan "Format timestamp tidak valid" beserta kode error INVALID_TIMESTAMP_FORMAT. Nonce divalidasi dengan memastikan bahwa nilai tersebut merupakan string dan memiliki panjang minimal 8 karakter. Jika validasi format nonce gagal, sistem mengembalikan respons kesalahan dengan pesan "Format nonce tidak valid. Nonce harus string minimal 8 karakter" dan kode error INVALID_NONCE_FORMAT.Langkah berikutnya adalah validasi timestamp masih dalam batas waktu yang valid. Sistem menghitung selisih waktu antara timestamp saat ini dengan timestamp yang diterima dari request. Timestamp saat ini dihasilkan menggunakan Math.floor(Date.now() / 1000) yang menghasilkan Unix timestamp dalam detik. Selisih waktu dihitung menggunakan Math.abs() untuk mendapatkan nilai absolut selisih waktu. Jika selisih waktu lebih besar dari TIMESTAMP_VALID_WINDOW yang ditetapkan sebesar 5 menit (300 detik), sistem mengembalikan respons kesalahan dengan status 401 dan pesan "Timestamp tidak valid. Harus dalam 5 menit terakhir" beserta detail informasi timestamp saat ini, timestamp yang diterima, dan selisih waktu dalam detik.Setelah validasi timestamp berhasil, sistem melakukan validasi nonce belum pernah digunakan sebelumnya untuk mencegah replay attack. Proses ini dilakukan dengan memeriksa keberadaan nonce dalam cache menggunakan cache.get() dengan kunci hmac_nonce_${nonce}. Jika nonce ditemukan dalam cache, berarti nonce tersebut sudah pernah digunakan sebelumnya dan sistem mengembalikan respons kesalahan dengan status 401 dan pesan "Nonce sudah pernah digunakan. Request ini mungkin merupakan replay attack" beserta informasi nonce dan waktu pertama kali digunakan. Jika nonce belum pernah digunakan, sistem menyimpan nonce ke dalam cache dengan TTL (Time To Live) selama 6 menit menggunakan cache.set(). Data yang disimpan dalam cache mencakup timestamp request, waktu penggunaan nonce, dan path endpoint yang diakses.Setelah semua validasi timestamp dan nonce berhasil, sistem menyiapkan data untuk verifikasi HMAC signature. Sistem membaca data dari request body dan membuat objek dataToVerify yang berisi field-field yang relevan untuk proses presensi. Field yang dimasukkan ke dalam objek verifikasi mencakup type untuk presensi biasa, latitude dan longitude untuk koordinat lokasi, lokasi_id untuk identifikasi lokasi kantor, dan id_kegiatan untuk presensi kegiatan. Sistem hanya memasukkan field yang nilainya tidak undefined atau null ke dalam objek verifikasi untuk memastikan konsistensi data. Timestamp dan nonce yang sudah divalidasi juga ditambahkan ke dalam objek verifikasi.Setelah objek verifikasi disiapkan, sistem memeriksa apakah objek tersebut tidak kosong. Jika objek kosong, sistem mengembalikan respons kesalahan dengan status 400 dan pesan "Request body tidak valid atau kosong" beserta kode error INVALID_REQUEST_BODY. Jika objek verifikasi tidak kosong, sistem memanggil fungsi verifyHMAC() dengan parameter objek verifikasi dan signature yang diterima. Jika verifikasi HMAC gagal, sistem menghapus nonce dari cache menggunakan cache.del() karena request tidak berhasil dan nonce tidak perlu dipertahankan. Sistem kemudian mengembalikan respons kesalahan dengan status 401 dan pesan "HMAC signature tidak valid" beserta kode error HMAC_SIGNATURE_INVALID.Jika semua validasi berhasil, termasuk validasi HMAC signature, timestamp, dan nonce, middleware memanggil fungsi next() untuk melanjutkan request ke controller berikutnya. Apabila terjadi kesalahan yang tidak terduga pada setiap tahap proses, middleware akan menangkap error melalui blok catch dan mengembalikan respons dengan status 500 Internal Server Error beserta pesan "Kesalahan dalam validasi HMAC" dan kode error HMAC_VALIDATION_ERROR. Secara keseluruhan, middleware validateHMAC menyediakan mekanisme keamanan berlapis yang memastikan setiap request yang masuk ke sistem adalah request yang valid, aman, dan belum pernah digunakan sebelumnya. Middleware dapat dilihat pada Gambar 5.11 dan 5.12 berikut.

4.Implementasi HMAC di Client (Mobile):
Implementasi HMAC di sisi client dilakukan pada aplikasi mobile menggunakan Flutter dengan bahasa pemrograman Dart. Class HmacUtils menyediakan berbagai method untuk menghasilkan HMAC signature yang konsisten dengan implementasi di server. Method generateHMAC() mengimplementasikan algoritma HMAC-SHA256 yang sama dengan backend, memastikan konsistensi dalam menghasilkan signature. Proses dimulai dengan mengambil secret key dari SharedPreferences atau menggunakan default secret key jika tidak tersedia di SharedPreferences. Secret key ini harus sama dengan secret key yang digunakan di server agar signature yang dihasilkan dapat diverifikasi dengan benar.Proses hashing dilakukan dengan melakukan sorting terhadap kunci-kunci data menggunakan data.keys.toList()..sort() untuk memastikan konsistensi urutan properti. Data yang sudah diurutkan kemudian dikonversi menjadi string JSON menggunakan jsonEncode(). String JSON ini kemudian di-encode menjadi UTF-8 bytes sebelum diproses menggunakan fungsi HMAC dari package crypto. Package crypto menyediakan class Hmac yang menerima algoritma SHA-256 dan secret key sebagai parameter. Instance HMAC kemudian mengkonversi data bytes menjadi digest yang kemudian dikonversi menjadi string hexadecimal sebagai signature akhir.Class HmacUtils juga menyediakan method generateKehadiranBiasaHMAC() yang khusus digunakan untuk menghasilkan HMAC pada proses presensi biasa. Method ini menerima parameter type (masuk atau keluar), latitude, longitude, lokasiId, serta parameter opsional timestamp dan nonce. Jika timestamp atau nonce tidak disediakan, sistem akan menghasilkan timestamp menggunakan generateTimestamp() yang mengkonversi waktu saat ini menjadi Unix timestamp dalam detik, dan menghasilkan nonce menggunakan generateNonce() yang menghasilkan string acak dengan panjang 32 karakter. Data yang akan di-hash terdiri dari type, latitude, longitude, lokasi_id, timestamp, dan nonce. Method kemudian memanggil generateHMAC() untuk menghasilkan signature dan mengembalikan objek yang berisi signature, timestamp, dan nonce.Demikian pula, class menyediakan method generateKehadiranKegiatanHMAC() yang digunakan untuk menghasilkan HMAC pada proses presensi kegiatan. Method ini memiliki struktur yang sama dengan generateKehadiranBiasaHMAC() namun menggunakan field id_kegiatan sebagai pengganti field type. Implementasi HMAC di sisi client memastikan bahwa setiap request presensi yang dikirim ke server disertai dengan signature yang valid, timestamp yang akurat, dan nonce yang unik, sehingga meningkatkan keamanan transmisi data dalam sistem informasi kehadiran berbasis lokasi ini. 5.1.1.5Kode Program Biometric Authentication dan Safe Device Detection
Untuk meningkatkan keamanan dan keabsahan proses presensi, sistem mengimplementasikan dua lapisan keamanan tambahan: autentikasi biometric dan deteksi keamanan perangkat. Autentikasi biometric memastikan hanya pemilik perangkat yang sah yang dapat melakukan presensi, sementara deteksi keamanan perangkat mencegah penggunaan aplikasi di emulator atau dengan lokasi palsu (fake GPS). Kombinasi ini memastikan bahwa setiap proses presensi dilakukan dari perangkat fisik yang sah dengan lokasi GPS yang valid dan dengan autentikasi biometric yang berhasil. 1.Fungsi isBiometricAvailable():
Fungsi isBiometricAvailable() adalah bagian dari class BiometricAuthHelper yang bertugas mengecek ketersediaan fitur autentikasi biometric pada perangkat. Fungsi ini menggunakan package local_auth yang menyediakan akses ke fitur biometric native perangkat seperti fingerprint (sidik jari) dan face recognition (Face ID). Proses pengecekan dimulai dengan memanggil _localAuth.canCheckBiometrics yang mengembalikan nilai boolean yang menandakan apakah perangkat memiliki kemampuan untuk melakukan pengecekan biometric. Pengecekan ini memverifikasi bahwa perangkat memiliki hardware biometric yang tersedia dan sistem operasi mendukung fitur autentikasi biometric. Hasil akhir dari fungsi ini adalah kombinasi logika AND antara hasil canCheckBiometrics dan isDeviceSupported(), sehingga hanya mengembalikan true jika kedua kondisi terpenuhi. Apabila terjadi kesalahan pada setiap tahap proses, fungsi akan menangkap error melalui blok try-catch dan mengembalikan nilai false, menandakan bahwa autentikasi biometric tidak tersedia pada perangkat tersebut. 2.Fungsi authenticate():
Fungsi authenticate() adalah bagian dari class BiometricAuthHelper yang bertugas melakukan proses autentikasi biometric pengguna. 3.Fungsi checkDeviceSafety():
Fungsi _checkDeviceSafety() adalah bagian dari halaman presensi yang bertugas melakukan pengecekan keamanan perangkat untuk mendeteksi apakah aplikasi berjalan di emulator atau menggunakan lokasi GPS palsu (mock location). Pembaruan state ini akan memicu rebuild widget dan menampilkan indikator visual kepada pengguna jika terdeteksi masalah keamanan perangkat. Apabila terjadi kesalahan pada proses pengecekan, fungsi akan menangkap error melalui blok try-catch dan mencatat error ke logger tanpa menghentikan eksekusi aplikasi. Setiap tab memiliki header yang menampilkan selector bulan menggunakan kalender untuk memilih bulan yang ingin ditampilkan riwayatnya, serta dropdown filter status yang memungkinkan pengguna memfilter data berdasarkan status tertentu seperti "Semua", "HADIR", "Tidak Hadir", "HAP", "HAS", "TAP", atau "CP". Dropdown filter untuk presensi kegiatan memiliki opsi yang lebih sederhana yaitu "Semua", "Hadir", dan "Tidak Hadir".
Daftar riwayat presensi ditampilkan dalam bentuk expandable list item yang dapat diklik untuk melihat detail lengkap. Setiap item menampilkan informasi tanggal presensi, status kehadiran dengan tag berwarna sesuai status, waktu check-in dan check-out jika tersedia, serta informasi lokasi presensi. Sistem menggunakan lazy loading dengan infinite scroll yang secara otomatis memuat data lebih banyak saat pengguna scroll mendekati akhir daftar, meningkatkan performa aplikasi dengan tidak memuat semua data sekaligus. Halaman ini dilengkapi dengan pull-to-refresh yang memungkinkan pengguna memperbarui data dengan menarik ke bawah. Indikator loading ditampilkan saat data sedang dimuat, dan jika terjadi error atau timeout, sistem akan menampilkan pesan error yang informatif. Sistem juga memiliki mekanisme fallback untuk mencegah loading state yang stuck dengan timeout 30 detik dan reset otomatis jika diperlukan. Fitur ini memastikan bahwa pengguna dapat melihat riwayat presensi mereka dengan mudah dan efisien, sehingga meningkatkan transparansi dan akuntabilitas dalam sistem informasi kehadiran berbasis lokasi ini. 5.2.   Pengujian Sistem
Pengujian sistem dilakukan untuk memastikan bahwa perangkat lunak yang telah dikembangkan berfungsi sesuai dengan rancangan dan kebutuhan pengguna. Pengujian ini dilakukan dengan menggunakan pendekatan Black box testing, yaitu pengujian yang berfokus pada hasil keluaran sistem berdasarkan masukan tertentu tanpa memperhatikan struktur internal kode program (Sommerville, 2016). Pendekatan ini digunakan untuk memastikan bahwa seluruh fungsionalitas sistem informasi kehadiran berbasis geo-location dapat berjalan dengan baik tanpa kesalahan selama penggunaan. Selain pengujian fungsional, dilakukan pula pengujian keamanan (Security-Oriented Black box testing) terhadap mekanisme HMAC, timestamp, dan nonce guna memastikan keamanan transmisi data presensi. Di akhir tahap pengujian, dilakukan User Acceptance Testing (UAT) yang melibatkan pengguna akhir dari Dinas Komunikasi dan Informatika Kota Pariaman untuk menilai tingkat penerimaan sistem. Hasil pengujian lengkap dapat dilihat pada Lampiran F.

5.2.2.Pengujian Fungsional (Functional Black box testing)
Pengujian fungsional dilakukan untuk memastikan bahwa seluruh fitur dan layanan pada sistem berjalan sesuai dengan spesifikasi yang telah ditetapkan. Pengujian ini menggunakan pendekatan Functional Black box testing, di mana setiap fungsi sistem diuji dengan memberikan berbagai variasi input dan memeriksa kesesuaian output yang dihasilkan dengan hasil yang diharapkan.
Pengujian ini mencakup seluruh komponen utama sistem, baik pada sisi aplikasi mobile maupun web admin. Fitur-fitur yang diuji meliputi proses autentikasi pengguna (login dan logout), pencatatan presensi masuk dan keluar dengan validasi lokasi, pengajuan dan persetujuan reset perangkat, pengelolaan data kegiatan dan lokasi presensi, serta penampilan data riwayat kehadiran.
Setiap skenario pengujian dirancang untuk menemukan kemungkinan kesalahan antarmuka, kesalahan proses logika, maupun ketidaksesuaian hasil keluaran terhadap spesifikasi sistem (Dwi Wijaya & Wardah Astuti, 2021). Pengujian dilakukan langsung oleh pengguna internal untuk memastikan bahwa seluruh alur fungsi berjalan sesuai kebutuhan operasional di Dinas Komunikasi dan Informatika Kota Pariaman. Hasil dari pengujian fungsional disajikan secara terperinci pada subbab berikutnya dalam bentuk tabel kasus dan hasil pengujian.

5.2.3.Pengujian Keamanan (Security-Oriented Black box testing)
Pengujian keamanan dilakukan untuk memastikan bahwa sistem mampu menjaga integritas dan autentikasi data selama proses komunikasi antara aplikasi mobile dan server. Pengujian ini menggunakan pendekatan Security-Oriented Black box testing, yaitu pengujian yang berfokus pada perilaku eksternal sistem untuk menilai kemampuan sistem dalam mendeteksi dan menolak data yang tidak sah tanpa melihat struktur internal kode program (Sommerville, 2016).
Fokus pengujian keamanan pada sistem ini adalah mekanisme Hash-based Message Authentication Code (HMAC) yang diimplementasikan pada setiap permintaan (request) presensi. Mekanisme HMAC berfungsi untuk memastikan keaslian dan integritas data yang dikirim dari aplikasi mobile ke server. Pengujian keamanan dilakukan melalui tiga skenario utama, yaitu validasi tanda tangan digital HMAC (HMAC signature validation), validasi timestamp, dan validasi nonce sebagai pencegahan replay attack.
Hasil pengujian menunjukkan bahwa sistem berhasil menolak seluruh permintaan yang tidak valid, seperti tanda tangan HMAC yang salah, timestamp yang telah kadaluarsa, maupun nonce yang sudah digunakan sebelumnya. Dengan demikian, dapat disimpulkan bahwa sistem memiliki mekanisme keamanan yang kuat untuk menjaga keaslian, integritas, dan validitas data presensi pegawai (Mustapha & Samanthula, 2024; Song, 2023).
5.2.3.1Validasi HMAC Signature, Timestamp, dan Nonce
Pengujian keamanan HMAC ini dilakukan secara otomatis oleh sistem pada setiap request presensi yang dikirim ke server. Tujuannya adalah memastikan bahwa sistem dapat memvalidasi HMAC signature dengan benar, menolak request dengan signature yang tidak valid, dan mencegah penggunaan nonce yang sama secara berulang. Hasil pengujian menunjukkan bahwa sistem berhasil memvalidasi HMAC signature dengan benar, menolak request dengan signature yang tidak valid, dan mencegah penggunaan nonce yang sama secara berulang. Hasil pengujian dapat dilihat pada Tabel 5.14 berikut.

Gambar 5. 50 Tampilan Request dengan Header HMAC

Server melakukan validasi keberadaan semua komponen tersebut terlebih dahulu. Jika salah satu komponen tidak tersedia, server mengembalikan respons error dengan status 401. Setelah semua komponen tersedia, server melakukan validasi format timestamp dan nonce. Timestamp divalidasi dengan memastikan bahwa nilai tersebut merupakan angka integer dan masih dalam batas waktu 5 menit dari waktu saat ini. Nonce divalidasi dengan memastikan bahwa nilai tersebut merupakan string dengan panjang minimal 8 karakter dan belum pernah digunakan sebelumnya dengan memeriksa cache.  Setelah validasi format berhasil, server memverifikasi HMAC signature dengan membandingkan signature yang diterima dengan signature yang dihasilkan dari data request menggunakan secret key yang sama. Sistem melakukan sorting terhadap kunci-kunci data untuk memastikan konsistensi format, kemudian mengkonversi data menjadi string JSON yang di-hash menggunakan algoritma SHA-256. Jika semua validasi berhasil, server memproses request dan menyimpan nonce ke dalam cache untuk mencegah penggunaan ulang dengan TTL (Time To Live) 6 menit. Setelah berhasil, sistem menampilkan log sukses dan memproses data presensi. Tampilan output pengujian keamanan HMAC (validasi berhasil) dapat dilihat pada Gambar 5.51 berikut.

Proses validasi HMAC juga dilengkapi dengan penggunaan crypto.timingSafeEqual() untuk membandingkan signature secara timing-safe, sehingga mencegah timing attack yang dapat membocorkan informasi tentang signature yang dibandingkan. Sistem juga menggunakan cache untuk menyimpan nonce yang telah digunakan dengan TTL 6 menit, yang lebih lama dari batas waktu valid timestamp (5 menit), sehingga memastikan bahwa nonce tidak dapat digunakan kembali meskipun dalam rentang waktu yang berbeda. Mekanisme ini memastikan bahwa setiap request presensi yang diterima adalah request yang valid, belum pernah digunakan sebelumnya, dan masih dalam batas waktu yang ditentukan, sehingga meningkatkan keamanan transmisi data presensi dalam sistem informasi kehadiran berbasis lokasi ini.
5.2.4.Pengujian UAT (User Acceptance Testing)
Pengujian ini dilakukan untuk mengevaluasi apakah sistem yang telah dikembangkan memenuhi kebutuhan pengguna dan dapat diterima secara luas. Pengujian dilakukan dengan menyebarkan kuesioner berisi beberapa pernyataan kepada pengguna internal, yaitu staf Dinas Komunikasi dan Informatika Kota Pariaman yang akan menggunakan sistem ini dalam aktivitas sehari-hari. Pemilihan responden menggunakan teknik purposive sampling. Purposive sampling adalah teknik pengambilan sampel dimana subjek dipilih secara sengaja berdasarkan kriteria tertentu yang dianggap relevan oleh peneliti yang memungkinkan peneliti untuk fokus pada subjek yang paling relevan dengan tujuan penelitian (Subhaktiyasa, 2024).
Pengujian ini melibatkan 5 responden yang terdiri dari satu Super Admin, dua Admin OPD/UPT, dan dua pegawai. Jumlah responden dianggap cukup representatif karena responden dipilih berdasarkan peran dan pengalaman menggunakan sistem presensi di lingkungan Dinas Komunikasi dan Informatika Kota Pariaman. Waktu yang dibutuhkan untuk setiap aktivitas utama, seperti presensi masuk dan pulang, dapat dipangkas secara drastis dari hitungan menit menjadi hitungan detik. Keuntungan utama sistem yang diusulkan adalah fleksibilitas lokasi presensi yang memungkinkan pegawai untuk melakukan presensi masuk langsung di lokasi kegiatan jika memiliki kegiatan pagi, dan presensi pulang langsung di lokasi kegiatan jika kegiatan berlangsung sore hari. Hal ini menghilangkan kebutuhan pegawai untuk bolak-balik ke kantor hanya untuk melakukan presensi, sehingga menghemat waktu perjalanan ±30–60 menit per hari bagi pegawai yang memiliki kegiatan lapangan. Selain itu, sistem juga memberikan manfaat tambahan berupa verifikasi lokasi presensi menggunakan GPS yang tidak tersedia pada proses manual, sehingga meningkatkan keabsahan dan akuntabilitas data kehadiran. Sistem juga dilengkapi dengan mekanisme keamanan HMAC signature yang mencegah manipulasi data presensi, sehingga data yang tersimpan lebih terjamin keasliannya. Hal ini menunjukkan bahwa sistem yang dibangun mampu mengoptimalkan kinerja pegawai, mempercepat alur kerja, mengurangi beban administratif, serta meningkatkan fleksibilitas dan keamanan dalam pengelolaan data kehadiran pegawai di Dinas Komunikasi dan Informatika Kota Pariaman.
5.4.   Kesimpulan Pengujian
Hasil pengujian fungsionalitas sistem yang dibangun berdasarkan fokus pengujian menunjukkan bahwa tidak ada kesalahan pada sistem. Oleh karena itu, dapat disimpulkan bahwa pembangunan Sistem Informasi Kehadiran Berbasis Lokasi pada Dinas Komunikasi dan Informatika Kota Pariaman berjalan sesuai dengan fungsional yang telah dirancang.
